# PA_TICKETS Gate T56 Result

**Branch:** `workstream-i-lifecycle-authority`  
**Scope:** minimal attachment-download authorization seam design  
**Review mode:** read-only architecture investigation; no implementation or provider operation

## Source-level call trace

`GET /api/v1/attachments/{id}/versions/{version}/download` is mapped by `AttachmentsController` under class-level `[Authorize]` and calls `IAttachmentService.DownloadAsync` (`src/PA.Tickets.Api/Controllers/AttachmentsController.cs:8,22`). `Program` runs authentication, password-rotation handling, authorization, and controller mapping before the action.

`AttachmentService.DownloadAsync` currently:

1. Queries `TicketsDbContext.Attachments` by attachment ID (`src/PA.Tickets.Infrastructure/Foundations/AttachmentService.cs:251-253`).
2. Queries `TicketsDbContext.Tickets` by the attachment's parent ticket ID (`line 254`).
3. Converts the ticket row to a domain `Ticket` and invokes `ITicketAccessAuthorizer.EnsureCanAccessAsync` (`line 255`).
4. Only after authorization queries the requested `AttachmentVersion` (`line 256`).
5. Only after that calls `IFileStorage.OpenReadAsync`, hashes the returned stream, and returns the stream (`line 257`).

The production policy remains `DatabaseTicketAccessAuthorizer` through `IAuthorizationService`; it requests `TICKET_READ` against the parent ticket resource. Storage is represented by the existing `IFileStorage` contract. No signed URL is generated by this path; the API streams content directly after checksum verification.

## Exact database coupling points

The `AttachmentService` primary constructor directly depends on `TicketsDbContext`, `ProviderTransactionRetry`, `AuditChainCoordinator`, `IFileStorage`, scanner, configuration, and `ITicketAccessAuthorizer`. Download specifically couples to three EF operations: attachment lookup, parent-ticket lookup, and version lookup. Other attachment/evidence methods also use the same context for writes, sequence access, work-item/attachment validation, audit/event persistence, and serializable transactions. Replacing the entire service for a hosted test would therefore bypass production authorization and storage ordering.

## Existing seams and narrowest proposal

The codebase already has the correct policy seam: `ITicketAccessAuthorizer` delegates to `DatabaseAuthorizationService` and must remain unchanged. It also has the correct content boundary seam: `IFileStorage` exposes `OpenReadAsync` without exposing credentials. What is missing is a download-specific metadata seam.

For a later, separately reviewed implementation gate, introduce a narrowly scoped contract in `PA.Tickets.Application.Foundations`, for example:

```csharp
public sealed record AttachmentDownloadOwnerFact(long AttachmentId, long TicketId, Ticket ParentTicket);
public sealed record AttachmentDownloadVersionFact(
    long AttachmentId, int VersionNo, string FileName, string? ContentType,
    long ContentLength, string StorageReference, string Sha256Hash);

public interface IAttachmentDownloadReader
{
    Task<AttachmentDownloadOwnerFact> ReadOwnerAsync(long attachmentId, CancellationToken ct);
    Task<AttachmentDownloadVersionFact> ReadVersionAsync(long attachmentId, int version, CancellationToken ct);
}
```

The production implementation would be an infrastructure adapter (for example, `EfAttachmentDownloadReader`) that performs the existing EF mappings and preserves the current not-found exceptions. `AttachmentService.DownloadAsync` would use the reader for owner/parent metadata, call the existing `ITicketAccessAuthorizer`, then use the reader for version metadata and the existing `IFileStorage` for content. The proposal deliberately does not expose `TicketsDbContext`, storage credentials, arbitrary queryables, or unrestricted content through the contract.

This is a design proposal, not an approved API. The exact record shape, namespace, and owner of the persistence adapter require code-owner review before implementation.

## Ordering and fail-closed invariants

- Attachment lookup and parent-ticket lookup precede the authorization decision exactly as today; missing rows retain the current not-found behavior.
- `ITicketAccessAuthorizer.EnsureCanAccessAsync` remains the sole authorization decision and receives the reconstructed parent ticket/resource.
- Version lookup occurs only after authorization succeeds.
- `IFileStorage.OpenReadAsync` occurs only after authorization and version existence checks.
- Checksum verification remains mandatory before returning content.
- Missing or unavailable owner/version facts fail closed with the existing exception-to-response mapping; no fallback to caller-supplied IDs, storage keys, or permissions is allowed.
- A denied request must not open a storage stream, disclose file bytes, or create a success audit event.

For hosted tests, a deterministic `IAttachmentDownloadReader` and recording `IFileStorage` could be injected while the real `AttachmentService`, `ITicketAccessAuthorizer`, `DatabaseAuthorizationService`, middleware, controller, and route remain active. An out-of-scope fact would assert 403 and zero storage reads; an in-scope fact would assert the checksum-verified harmless stream. This would prove application ordering only, not EF translation, storage ACLs, signed URLs, or production persistence.

## Behavior-preservation risks

1. **Exception ordering:** combining owner and version reads into one method could change 404 versus 403 behavior. Keep the two-stage contract to preserve current ordering.
2. **Resource fidelity:** the owner fact must carry every parent-ticket field used by `AuthorizationResource` (department, team, client, assignee, ID). Dropping a field could broaden or narrow scope.
3. **Version substitution:** the second read must bind both attachment ID and requested version and return the stored hash/reference from the same row; callers must not supply a storage key.
4. **TOCTOU:** metadata can change between owner authorization and version read. Provider-backed validation is still required for revocation, attachment replacement, and transaction semantics.
5. **Storage disclosure:** a fake storage test cannot establish production ACLs, signed URL policy, object-key secrecy, or checksum behavior against a real store.
6. **DI parity:** production must register the EF adapter and continue registering `AttachmentService`; tests may override only the new reader and storage contracts, never the authorization service.

## Existing coverage and limitations

`PostgreSqlAttachmentEvidenceTests.Attachment_and_evidence_access_uses_ticket_authorization_for_metadata_versions_download_and_review` covers service-level ownership/download/review behavior but is provider-gated. No T43–T55 hosted test exercises an attachment/evidence controller route. T55 correctly concluded that replacing `IAttachmentService` would be dishonest because it bypasses the production service boundary. The proposed seam addresses that architectural limitation without moving policy into a test double.

Provider-backed evidence remains required for EF/Npgsql translation and materialization, attachment/version ownership, storage persistence, transaction/audit atomicity, checksum and cleanup behavior, concurrent replacement, and error semantics after connection loss.

## Recommendation

Implement the seam in a later gate only after application/infrastructure code-owner review confirms the two-stage contract and exception compatibility. That gate should add one hosted download denial test using the real service/policy path and recording storage fake, followed by separately approved provider validation. Until then, leave attachment/evidence routes provider-gated; do not add a controller-only test or replace the service with a test authorization mock.
