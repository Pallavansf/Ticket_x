# Production security configuration

## Current implementation

The API implements app-managed username/password login at `POST /api/v1/auth/login`. It verifies ASP.NET Core Identity password hashes stored in the nullable `PA_TICKETS_USER.S_PASSWORD_HASH` column and issues short-lived HMAC-SHA256 bearer tokens. Supply `Auth:Local:SigningKey` through protected configuration; it must contain at least 32 UTF-8 bytes and must never be committed. `Auth:Local:Issuer`, `Auth:Audience`, and `Auth:Local:TokenLifetimeMinutes` configure token validation and lifetime. Production requires the local signing configuration; the test-only `Auth:TestSigningKey` is rejected outside `Testing`.

`POST /api/v1/admin/users/{id}/password` sets or resets a password and requires the existing `USER_ADMIN` permission. Passwords are hashed, never returned by user administration, and password changes are written to the administration audit chain without recording the password/hash. Administrative password resets set a mandatory next-login rotation flag. Accounts carrying a rotation-required local JWT may use only `POST /api/v1/auth/change-password` and the public login route until they change the password and log in again.

Application RBAC remains database-backed: issued role/permission claims support UI presentation, but API authorization resolves active users, effective memberships, role-permission mappings, and resource scopes from the database. A configurable-RBAC implementation and PostgreSQL/Oracle migration 031 drafts are present in the worktree, but are not reviewed, applied, provider-validated, or approved for deployment. The five built-in roles, custom-role administration, scoped grants, delegation, and Angular role editor therefore remain unaccepted. The current 030 SQL files are superseded and must not be executed. See the [configurable RBAC design and migration plan](./PA_TICKETS_CONFIGURABLE_RBAC_DESIGN.md); the earlier [five-role review](./PA_TICKETS_FIVE_ROLE_RBAC_REVIEW.md) is retained only for audit context. OIDC bearer validation remains an optional future integration and is not required for local username/password acceptance.

## Selected authentication direction

Local acceptance uses application-managed username/password authentication and database-backed RBAC. The target model has five protected built-ins—`USER`, `ADMIN`, `SUPER_ADMIN`, `ADMIN_HEAD`, and `SPECTATOR`—plus Super Admin-managed custom roles. Draft code for custom roles, configurable grants, explicit scopes, delegation, and the Angular role editor is present but has not passed database integration or real browser acceptance. The code fails authorization closed when required permission metadata is missing; the 031 migration is required before those paths can operate. Super Admin permission mappings are locked until a separately reviewed two-person workflow exists. Do not treat the configurable design or migration drafts as an executed migration/account transition. OIDC/SSO is a future optional add-on and is not a local acceptance prerequisite. Bootstrap operation, password reset operations, distributed abuse protection, production secret rotation, and live browser-to-API acceptance must be operationally reviewed before release.

Production CORS requires one or more explicit HTTPS origins in `Cors:AllowedOrigins`. Wildcards, HTTP origins, and implicit localhost defaults are rejected. Development retains the localhost origin default. The API redirects HTTP to HTTPS and enables HSTS in production.

Forwarded headers are ignored by default. When TLS is terminated at a reverse proxy, enable `ForwardedHeaders:Enabled` and configure every trusted immediate proxy IP under `ForwardedHeaders:KnownProxies`. The API accepts one forwarded hop and does not trust headers from arbitrary clients. Without this explicit configuration, terminate TLS directly at the API.

Supply local signing keys and any optional OIDC values through the deployment's protected configuration/secret mechanism; do not commit signing secrets or database credentials. For local Development, the `http` launch profile binds `http://localhost:5018`, but startup fails closed unless `Auth__Local__SigningKey` is provided to the API process by an approved local secret store or protected, process-scoped environment injection. The key must contain at least 32 UTF-8 bytes; the Development config supplies issuer, audience, and a 30-minute lifetime. The API project does not declare a `UserSecretsId`, so `dotnet user-secrets` is not currently initialized for it; do not add one or store a value without owner approval. The project owner must arrange the approved secret source and deliver the key locally without putting it in launch settings, appsettings, command-line arguments, source control, or logs. OIDC issuer/authority settings are only required when the optional OIDC bearer scheme is enabled.

## Initial administrator provisioning

There is intentionally no public, unauthenticated bootstrap endpoint and no default administrator credential. Do not expose or temporarily add an HTTP route that grants `USER_ADMIN` or an administrator role.

The repository includes `tools/PA.Tickets.Bootstrap`, an interactive PostgreSQL-only, one-shot operator utility. It provisions `SUPER_ADMIN` but has not been approved for use with migration 031. The current migration 030 is superseded; do not run the utility until migration 031 has been independently reviewed and applied and the operator/account transition is separately approved. The utility requires process-scoped `PA_TICKETS_BOOTSTRAP_CONNECTION_STRING`, `PA_TICKETS_BOOTSTRAP_EXPECTED_DATABASE`, `PA_TICKETS_BOOTSTRAP_EXPECTED_ROLE`, and `Database__Provider=PostgreSQL` settings; compares the live database/user identity with the explicitly configured expected target; requires exact typed confirmation; and reads a 16-character-minimum temporary password without echo or command-line arguments. It refuses if an active legacy `ADMINISTRATOR` or `SUPER_ADMIN` membership or either historical bootstrap marker exists. User, role membership, and audit events are committed in one serializable transaction. It sets `N_PASSWORD_ROTATION_REQUIRED`, and there is no public privileged-account creation endpoint.

1. Obtain a tracked change approval naming the account owner, operator, exact target environment/database, and a second reviewer. Run the utility only from a controlled operator workstation after reviewing its source/build and applying the provider-specific additive migration. The current utility supports PostgreSQL only; Oracle provisioning is not implemented or claimed.
2. Supply the connection and expected identity through process-scoped protected configuration, never as command-line arguments or committed settings. Keep ordinary client access blocked during provisioning. Confirm the utility prints the exact approved non-secret database/user target; stop on any mismatch.
3. Enter the named owner account and type the exact requested `INITIALIZE SUPER ADMIN <database> <login>` confirmation. Generate a temporary password in an approved secret manager and enter it at the hidden prompt. The utility prompts twice and stores only an ASP.NET Core Identity password hash.
4. Deliver the temporary credential to the account owner through the approved secret-delivery channel. Verify login returns a rotation-required token; protected API access must be denied until the authenticated password-change endpoint succeeds. Re-login with the owner-controlled password and verify the rotation flag is clear and a `SUPER_ADMIN`-protected operation is allowed.
5. Have the second reviewer confirm the administrator’s effective grants and account status. Remove the temporary secret from the secret manager, close the bootstrap change, and prevent routine application deployment identities from invoking the utility. Preserve audit evidence, not the password or hash.

**Verification limitation:** the bootstrap utility builds but has not been executed against a live database, and the operator/owner delivery, second-review, and `USER_ADMIN` acceptance steps remain unverified. Do not treat this runbook as evidence that an administrator has been provisioned or that deployment is ready. Do not improvise direct production SQL or bypass authorization.

The one-shot guard is enforced by active administrator membership and an audit marker in the same database; it is not an independent immutable anchor. Restrict database-owner access and retain bootstrap change/audit evidence outside the application database under the organization's approved controls.

## Five-role administration and reporting hierarchy

The implementation recognizes `SUPER_ADMIN` as the organization-wide administrative role. Existing role ID/code `ADMINISTRATOR` is preserved without promotion or reinterpretation; runtime policy ignores its prior global grants and permits only scoped ticket read/update. User rows retain the self-referencing `N_MANAGER_USER_ID`, but that reporting relationship is neither an authorization scope nor an Admin Head delegation.

Super Admin user-list access is organization-wide. Admin user management is limited to the actor's department. Admin Head user management is limited to the actor's department plus specifically delegated Admins, checking both an effective delegation and the target's active Admin membership. Profile changes still accept display name, email, and phone only; role, permission, client, department/team, active status, and reporting-manager fields are not accepted through the profile endpoint.

Account activation/deactivation, password reset, reporting-manager maintenance, and department/team operations use `USER_ADMIN` or the separately restricted `CONFIG_ADMIN`; role membership assignment/removal uses `ROLE_ADMIN`; client-membership assignment/removal uses `CLIENT_ADMIN`. Self-service profile authority grants none of these. Ordinary role assignment rejects self-change, the legacy `ADMINISTRATOR` role, compatibility roles, and privileged grants by non-Super-Admins. Admin and Admin Head role changes are target-scoped. Role/account mutations validate permission and target inside serializable transactions.

`PUT /api/v1/admin/users/{id}/reporting-manager` remains a separate `USER_ADMIN`-gated operation. It rejects self-management, cycles, inactive managers, and placing a Super Admin under another manager; a department administrator cannot link users across departments. Profile and hierarchy changes use serializable transactions. Sensitive profile audit records contain actor, target, changed fields, timestamp, and before/after values; audit storage consequently contains personal data and requires restricted access.

Email values are format-checked and unique case-insensitively for profile updates and account creation; the database unique index is the final concurrency guard. A changed email is marked unverified and never becomes verified merely through profile administration. The repository has no email-sender abstraction for identity confirmation, configured `Communication:Providers:Email` value, confirmation endpoint, or verification policy. A single-use challenge cannot be delivered without disclosing it in an ordinary response or inventing a provider. Do not issue verification challenges until an approved delivery adapter and operational sender configuration exist, and the owner approves challenge expiry, resend and confirmation rate limits, replay handling, invalidation after another address change, verification's effect on account access, and audit evidence. Successful verification, expiry, replay, and delivery are therefore not implemented or accepted. The configurable RBAC migration drafts have not been executed against PostgreSQL or Oracle; provider validation remains pending.

The current permission-metadata design, role-combination deny rule, scope/delegation model, and pending legacy-account transition are recorded in [the configurable RBAC design](./PA_TICKETS_CONFIGURABLE_RBAC_DESIGN.md). The draft has not passed role integration, migration repeatability, data-preservation, or full browser/API acceptance tests. Do not run migration 030 or 031 or provision/transition an account until the migration and target identity have been independently reviewed and explicitly approved.

## Login abuse and token revocation

`POST /api/v1/auth/login` has an in-process fixed-window limit of five requests per minute per observed remote IP, with no queue. Unknown users, disabled accounts, and bad passwords share the same generic 401 response; the unknown-user path verifies a dummy password hash. A rate-limited response is a generic 429. The focused regression verifies five generic failures followed by throttling. This is not persistent per-account lockout, cross-instance throttling, or abuse monitoring. Production requires trusted proxy/client-IP configuration and a distributed gateway or limiter, monitoring/alerting, and an operational response procedure; do not claim account-abuse protection is complete.

Bearer tokens are self-contained and remain cryptographically valid until expiry. API permission and resource checks consult the database on protected operations, so deactivating a user or removing role membership denies subsequent protected operations even with an unexpired token. There is no token denylist or refresh-token/revocation service; endpoints that only rely on authentication without an application authorization check must not be assumed to revoke immediately. Keep token lifetimes short and use signing-key rotation for emergency global revocation, recognizing that rotation invalidates every token signed by that key.
